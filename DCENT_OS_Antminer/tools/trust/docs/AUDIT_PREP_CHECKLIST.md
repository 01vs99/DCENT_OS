## 1. Proposed scope (three work packages)

**WP-1 — Firmware supply chain & reproducibility**
- Commit-pinned builds: manifest `source_commit` ↔ public tag ↔
  `source-closure.json` round-trip on a sample of `____` targets.
- Reproducibility: rebuild from the tag in a clean container; compare
  SHA-256 to the manifest (report any non-reproducing target as a finding).
- Dependency evidence integrity: do the shipped
  `*.rust-dependencies.json` / `*.buildroot-legal.json` match an independent
  resolution of `Cargo.lock` / `make legal-info` at that commit?
- SBOM fidelity: do published CycloneDX/SPDX SBOMs (generated by
  `tools/trust/sbom_from_drop.py`) faithfully map that evidence without
  overstating claims (reachability, license audits)?

**WP-2 — Release signing & channel integrity**
- Ed25519 lane: manifest / per-artifact / feed signature coverage; are there
  publishable files that escape signature coverage?
- Verify tool soundness: `tools/trust/verify_release.py` — fail-closed
  behavior, fingerprint pinning, downgrade/mixed-drop attack resistance
  (can a valid old manifest be replayed for a newer board?).
- Key ceremony docs vs practice gap analysis (template §1–§7 of
  `KEY_CEREMONY_TEMPLATE.md`).
- Channel feed: `dcentos.signed-channel-feed/v1` envelope — signature
  scope, replay, rollback (`minimum_version` enforcement client-side).

**WP-3 — Daemon network surface (dcentrald)**
- Listening sockets by default image; auth on every control path (MCP
  posture: read open, write fails closed without a token — verify no
  regression).
- Stratum egress behavior; no telemetry/phone-home claim verification
  (see `NO_TELEMETRY_STATEMENT.md`) — confirm default-off by network
  observation in the audit lab, not just code review.
- Dashboard/API input validation at boundaries; secrets handling.

Out of scope (declare): live-hardware actions (audit is desk/lab only),
pool software, toolbox PyPI packaging (separate engagement if desired).

## 3. Artifact bundle to hand the auditor (one directory, read-only)

1. **Source tag export**: git archive of `dcentos-drop1-beta-20261002`
   (+ later drops in scope), or the GitHub tag ref.
2. **Drop manifests + signatures**: `MANIFEST_DROP1_*.json` + `.sig`, per-set
   `producer-result.json*`, `release-invocation.json`.
3. **SBOMs**: per-image `*.sbom.cyclonedx.json` / `*.sbom.spdx.json` + the
   generator source (`tools/trust/sbom_from_drop.py`).
4. **Dependency evidence**: the signed `*.rust-dependencies.json` and
   `*.buildroot-legal.json` set for the sampled targets.
5. **Gate transcripts**: offline-gate + blocking-gate logs for the audited
   commit (from the release run dir), hardware-enablement matrix.
6. **Threat model**: current STRIDE-style doc for the firmware install path
   and update channel (owner: A6/A9 wave2 deliverable — attach when written;
   if absent at engagement start, mark as auditor-visible gap).
7. **Verify tool + docs**: `verify_release.py`, `VERIFY_A_RELEASE.md`,
   `KEY_CEREMONY_TEMPLATE.md`, `NO_TELEMETRY_STATEMENT.md`.
8. **No-telemetry technical backing**: network-egress inventory of a default
   boot (firewall deny-log capture from the audit lab).

Every item ships with its SHA-256 in an accompanying `BUNDLE_MANIFEST.json`
signed with the release key (same lane as drops).
